# 局域网远程游戏资源流式传输评估

## 1. 结论

`krkrgo` 可以引入基于 C/S 的远程游戏资源传输。客户端继续执行 TJS、KAG、图像合成、音频输出和视频呈现，服务端提供资源清单、资源字节和媒体区段。

流畅体验需要三条管线协同：网络读取、后台解码、播放队列。音频回调和渲染线程从本地队列取数据，网络请求、磁盘访问和解码任务由后台 worker 处理。

对于首次启动、部分内容访问和多次运行复用缓存的场景，按需传输通常比先传输完整 XP3 更省启动时间和网络流量。完整访问全部素材时，完整 XP3 拥有较低的请求数量，整体效率取决于压缩率、缓存命中率和资源访问顺序。

## 2. 目标与范围

目标如下：

- 传输脚本、图片、视频、音频等游戏资源。
- 客户端完成脚本执行、解码、渲染和音频输出。
- 局域网环境下保持稳定的音频连续性和视频帧率。
- 支持首次运行、重复运行、资源版本更新和断线恢复。
- 保留现有 XP3、TJS、KAG 和媒体路径语义。

本文讨论资源传输，不讨论远程桌面或游戏画面传输。

## 3. 当前项目基础

### 3.1 存储抽象

[`internal/assets/content_storage.go`](../internal/assets/content_storage.go) 已提供 `ContentBackend` 接口：

- `Open(path)` 返回随机读取文件和文件大小；
- `ReadDir(path)` 提供目录清单；
- `Stat(path)` 提供资源元数据。

这套接口已经用于 URI 项目存储。HTTP 客户端可以实现同一接口，将服务端资源映射为项目树。

### 3.2 XP3 支持

[`internal/assets/storage.go`](../internal/assets/storage.go) 的内容后端可以挂载远程 XP3。XP3 索引和数据段使用 `ReaderAt` 读取，因此远程客户端可以使用 Range 请求取得所需区段。

当前 `Storage.Read` 返回完整 `[]byte`。普通资源读取会取得完整文件，XP3 资源读取会取得所需成员数据。这个接口适合脚本、图片和短音频，长音频与视频需要新的读取接口。

### 3.3 当前媒体路径

- [`internal/media/ffmpeg/decoder.go`](../internal/media/ffmpeg/decoder.go) 使用内存数据创建 FFmpeg 输入源。
- [`internal/runtime/sound.go`](../internal/runtime/sound.go) 将音频解码为完整 PCM 后交给声音对象。
- [`internal/runtime/video.go`](../internal/runtime/video.go) 从完整媒体数据创建视频解码器，再持续取得视频帧。
- 图片加载路径读取完整资源，再执行图片解码和图层提交。

当前实现具备媒体解码能力，流式输入仍需要新的数据源和后台调度层。

### 3.4 已有设计方向

[`docs/launcher.md`](launcher.md) 已记录资源清单、HTTP 存储和本地缓存的未来方向。这与本文方案一致。

## 4. 与完整 XP3 传输的比较

| 指标 | 完整 XP3 | 按需资源传输 |
|---|---|---|
| 首次启动 | 等待完整包体后开始 | 先取清单、启动脚本和首场景资源 |
| 部分内容访问 | 会携带大量后续素材 | 传输实际访问的资源 |
| 全部内容访问 | 请求少，压缩集中 | 请求多，资源级缓存更灵活 |
| 重复运行 | 整包缓存有效 | 按哈希复用单个资源或区段 |
| 长媒体播放 | 本地读取路径简单 | 需要预读、队列和后台解码 |
| 资源更新 | 通常重新处理整包 | 可以更新清单中的部分资源 |

推荐采用混合形态：小资源使用完整资源请求，视频和长音频使用区段请求，XP3 继续作为服务端资源格式之一。

## 5. 推荐总体架构

```text
服务端
  资源清单 / 版本 / 哈希 / 媒体区段索引
        │
        │ HTTP/2、QUIC 或局域网自定义协议
        ▼
客户端资源层
  清单缓存 → 区段缓存 → ContentBackend → Storage
        │
        ├── 脚本与图片：完整资源读取、后台预取
        │
        └── 音频与视频：Range/区段读取、后台解码
                         │
                         ▼
                  PCM 队列 / 视频帧队列
                         │
                         ▼
                  音频混合器 / Ebitengine
```

### 5.1 服务端资源清单

清单至少包含：

- 项目版本和资源版本；
- 资源路径、类型、大小和内容哈希；
- XP3 文件索引信息；
- 媒体区段大小、时间范围和关键帧位置；
- 资源之间的预取提示；
- 支持的编码格式和协议版本。

启动阶段可以根据清单得到首批资源，后续请求按照脚本和播放状态产生。

### 5.2 客户端资源层

客户端需要三个缓存层：

1. 内存缓存：保存近期使用的图片、脚本和媒体区段。
2. 磁盘缓存：保存内容哈希对应的完整资源或区段。
3. 播放队列：保存已解码的 PCM 和视频帧。

网络读取结果先进入磁盘或内存缓存，再交给解码器。缓存条目使用内容哈希标识，资源更新通过新清单触发。

### 5.3 请求调度

请求优先级建议如下：

1. 当前音频播放区段；
2. 当前视频帧所需数据；
3. 下一段音频和视频；
4. 即将显示的图片；
5. 后续脚本和普通资源。

请求调度器需要支持取消旧请求、合并相邻区段、限制并发数量和记录每个请求的耗时。

## 6. 音频流式方案

音频管线建议为：

```text
编码资源区段
  → 网络区段缓存
  → demux
  → 解码 worker
  → PCM 队列
  → 音频混合器
```

核心要求：

- 首次播放前积累足够的 PCM 缓冲；
- 播放过程中持续保持高水位预取；
- 网络请求和解码任务不进入音频回调；
- 队列低于阈值时提高当前音频请求优先级；
- 音频区段包含时间信息，支持恢复和定位；
- 循环播放资源保留本地缓存，减少重复请求。

当前 `WaveSoundBuffer.OpenBytes` 需要增加面向连续 PCM 生产的接口。现有完整 PCM 路径可以继续服务于短音效，长背景音乐使用新的流式路径。

## 7. 视频流式方案

视频管线建议为：

```text
媒体区段
  → Range/区段缓存
  → FFmpeg 输入读取器
  → demux 与视频解码 worker
  → 有序视频帧队列
  → Ebitengine 图像呈现
```

关键设计：

- 区段从关键帧开始，便于启动和定位；
- 音频区段与视频区段共享时间轴；
- 解码 worker 维护若干待显示帧；
- 播放线程只消费已经完成的帧；
- 跳转时根据关键帧索引选择新区段；
- 视频区段与音频区段使用同一资源版本。

现有 FFmpeg 自定义 AVIO 需要增加远程输入源。该输入源应支持读取、定位、文件大小查询和区段缓存。FFmpeg 的 seek 可能访问文件头、索引和文件尾部，因此读取器需要合并请求并缓存近期访问区域。

## 8. 图片与脚本方案

图片和脚本可以先采用完整资源读取：

- 启动脚本和首场景图片进入启动集合；
- 后续资源由后台任务预取；
- 图片解码在后台执行；
- 图层提交发生在运行时安全时点；
- 图片的 `_m`、`_p` 等关联资源与主资源使用同一请求组。

TJS 和 KAG 可能动态构造资源名。清单可以提供静态预取提示，运行时仍需要保留按路径查询能力。

## 9. 关键风险

### 9.1 音频队列耗尽

这是流畅体验的最高风险。网络延迟或解码抖动让 PCM 队列变空时，会产生停顿、爆音和音画不同步。

### 9.2 视频解码高峰

高分辨率、复杂编码和关键帧解码会带来瞬时 CPU 峰值。视频帧队列需要覆盖解码高峰，过期帧需要及时释放。

### 9.3 随机读取造成请求放大

媒体容器可能读取多个索引区域。简单的单次 Range 实现会产生大量小请求，局域网带宽充足时仍可能出现播放等待。

### 9.4 资源依赖遗漏

KAG/TJS 可能动态生成资源路径，图片可能关联 `_m`、`_p` 等旁车资源，XP3 还可能涉及保护过滤器。清单和动态查询需要同时存在。

### 9.5 异步事件顺序

资源请求完成顺序会改变。图片完成事件、脚本回调、视频状态事件需要使用请求编号或资源代次判断旧结果。

### 9.6 版本混用

旧脚本、新图片和旧音频可能产生尺寸、时间轴或接口不匹配。清单版本和内容哈希需要贯穿请求、缓存和解码器。

### 9.7 内存与磁盘增长

网络缓存、解码帧、PCM 队列和磁盘缓存同时存在时，大媒体会产生明显资源占用。需要分别设置网络缓存、解码缓存和持久缓存上限。

### 9.8 断线与数据损坏

区段请求需要重试、校验和恢复策略。播放系统应保留已经取得的缓冲，并在队列耗尽前完成下一次请求。

### 9.9 服务端并发压力

多客户端同时请求相同区段时，服务端磁盘读取、连接数和请求调度会成为新的瓶颈。服务端需要支持缓存热点区段和并发限制。

### 9.10 资源安全

脚本由客户端执行，服务端资源具有可执行内容属性。部署时应使用身份校验、传输加密、清单签名或内容哈希校验。

## 10. 协议建议

协议可以从 HTTP/2 开始，原因是连接复用、Range 请求和调试工具都较成熟。QUIC 适合后续需要更快恢复和多路传输的场景。

建议接口形态：

```text
GET /v1/projects/{project}/manifest
GET /v1/assets/{hash}
GET /v1/assets/{hash}  Range: bytes=start-end
GET /v1/media/{hash}/segments/{index}
```

响应需要包含资源版本、哈希、长度、区段编号和校验信息。客户端可以将完整资源和媒体区段统一保存为内容哈希对象。

## 11. 流畅性验证指标

实现阶段应记录：

- 冷缓存启动时间和热缓存启动时间；
- 首个脚本、首张图片、首个音频样本、首个视频帧的可用时间；
- 音频 PCM 队列最小深度；
- 视频帧队列最小深度；
- Range 请求延迟的中位数和 P95；
- 播放停顿次数与累计停顿时间；
- 音频与视频时间差；
- CPU、内存和磁盘缓存占用；
- 断线、重试和缓存校验结果。

测试应覆盖冷缓存、热缓存、多个客户端并发、短暂网络延迟、区段重试、视频跳转和完整游戏流程。

## 12. 建议实施顺序

1. 为资源读取增加请求耗时、缓存命中和队列深度统计。
2. 实现基于 HTTP Range 的 `ContentBackend` 和磁盘区段缓存。
3. 先接入脚本、图片和短音效的按需读取。
4. 为 FFmpeg 增加远程读取器和后台 demux worker。
5. 为长音频增加连续 PCM 队列。
6. 为视频增加关键帧索引、帧队列和音视频时钟。
7. 增加版本校验、断线恢复、并发控制和缓存清理。
8. 使用真实游戏项目进行窗口启动和连续播放测试。

## 13. 最终判断

基于资源的 C/S 传输适合 `krkrgo`。流畅体验的核心在于后台网络读取、后台解码和有容量限制的播放队列。

小资源可以采用完整资源缓存，大媒体应采用 Range 或媒体区段流式读取。完整 XP3 可以继续作为服务端存储格式，客户端按索引和区段取得内容。

当前项目最需要新增的能力是：远程随机读取器、媒体后台解码器、音频 PCM 队列、视频帧队列、内容哈希缓存和可观测性指标。
