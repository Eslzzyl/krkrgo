# Runtime and Native Services Porting Status

## Session and dispatch model

[`runtime.Session`](../internal/runtime/session.go) owns a TJS VM, runtime `Services`, and a shared execution budget. [`Services`](../internal/runtime/services.go) owns host-independent state and implements the TJS host-call boundary. [`NativeRegistry`](../internal/runtime/native.go) installs operation names and routes calls to services. This permits deterministic/headless use and interactive hosting; it does not create OS UI services by itself.

Native methods are bounded surfaces aligned with selected C++ behavior. Registration is in `session.go`/`native.go`; current behavior is summarized by domain below.

## Date

`Session` registers the TJS `Date` class using the existing `tjs.Date` calendar and parser implementation. The bounded bridge provides constructor initialization, date getters and setters, `getTime`/`setTime`, instance `parse`, and static `getTimezoneOffset`; stored timestamps retain the Go implementation's millisecond precision.

The TJS `Math` namespace exposes constants and the implemented numeric operations through the runtime native. `Math.random` uses the TJS xorshift generator (initialized with a fixed seed and explicitly seedable); its generator is package-level rather than session-local.

## Time and storage compatibility

Headless sessions advance a virtual clock as replay time moves forward; script waits are fulfilled by advancing that clock rather than sleeping for wall-clock time. The replay step defaults to 16 ms, with action timestamps and checkpoints evaluated against the same session timeline.

`Storages.fstat(path)` is implemented for the active project storage and returns a dictionary containing the resource `size`. It works for loose files and entries resolved from mounted XP3 archives; unavailable storage and missing-resource errors are not converted into fabricated metadata. This is a bounded file-size query, not the full `fstat.dll` mutation or directory API.

`Storages.setXP3ArchiveExtractionFilter(callback)` installs the project's XP3 protected-entry callback; passing `void` clears it. A loose root-level `xp3filter.tjs` is executed before `startup.tjs`, so it can register the callback before protected resources are read. The callback receives `(fileHash, offset, buffer, size, fileName, context)` after decompression and before the entry checksum; its mutable Octet buffer must be transformed into checksum-valid plaintext. Callback errors and checksum mismatches fail the resource read.

`Storages.dirlist(dir)` and `Storages.dirlistEx(dir)` implement the read-only directory enumeration of `fstat.dll` for the active project storage. Both require the name to end with a directory separator (`/`, or a native `\`), resolve it with the storage's case-insensitive component lookup and symlink containment, and return the direct children of that directory without recursing, sorted by name for deterministic replays: `dirlist` yields an array of entry names in their on-disk spelling, and `dirlistEx` yields an array of dictionaries with `name`, `size` (0 for directories), `attrib`, `mtime`, `atime`, and `ctime`. `attrib` carries POSIX permission bits plus the `S_IFDIR` (0x4000) and `S_IFREG` (0x8000) file-type bits, so scripts can test it for directory status as the plugin manual instructs; the timestamps are Unix seconds, using the file metadata's access/creation times on Windows and falling back to the modification time elsewhere. Names that leave the project (`..`, absolute paths), name a regular file, or address an archive directory are rejected, and the listing never enumerates XP3 archive contents. Focused behavior tests cover name listing, metadata fields, case-insensitive resolution, and rejection of invalid directory names.

`TextStream.write(path, text, mode?)` honors the optional `oN` offset parsed from the mode string. A write at an offset replaces bytes from that position while preserving the preceding prefix; an offset at the current end appends, and gaps are zero-filled. File-path writes remain confined to the save overlay. Focused behavior tests cover `"o4"` replacement, `"o15"` append, and `Dictionary.saveStruct` with `"zo10"` followed by `Scripts.evalStorage(..., "o10")` reading the serialized value at that offset.


## System, storage, clipboard, and scripts

- [`system_native.go`](../internal/runtime/system_native.go) implements selected `System` values and operations: version/platform/width values, event/window flags, UUID generation, callbacks, cache/compaction/message operations, key state, and explicit termination requests. `System.getKeyState(key, current=true)` reads held keys/buttons from headless input events; `current=false` reads and consumes the recent-down state. A query in either mode clears that key's recent-down latch, and without input events both modes return `0`. `System.getArgument` uses exact key lookup; `System.setArgument` stringifies and stores values, with `void` stored as the empty string. Window/display-related operations also use [`window_native.go`](../internal/runtime/window_native.go).
- [`storages_native.go`](../internal/runtime/storages_native.go) exposes path helpers, project-storage queries, auto paths, and archive-cache clearing. `Storages.getLocalName` maps local file-media names to OS paths and rejects archive members, which have no single local path. `Storages.isExistentStorage` checks the save overlay before project storage; `TextStream` reads/writes resolve local `file://.` URIs under the configured save directory or project, with writes confined to the save overlay. File-media limits are in [Assets, storage, and media](assets-storage-media.md).
- [`clipboard_native.go`](../internal/runtime/clipboard_native.go) supplies a static, text-only `Clipboard.asText`/`hasFormat(1)` path through `atotto/clipboard`. Linux helper requirements are in [Host and platform](host-platform.md).
- [`scripts_native.go`](../internal/runtime/scripts_native.go) implements the supported source execution/evaluation, text-encoding, VM trace, and class-name surface. See [TJS and KAG](tjs-kag.md) for specific language/runtime gaps.

## Window focus

`Window.focusedLayer` returns the original `Layer` object when a layer has focus, or `null` when none does. Assigning a `Layer` requests focus through the same layer focus transition used by `Layer.focus()`; assigning `null` (or `void`) clears focus. Invalid non-Layer objects are rejected. Focus changes continue to update the `Layer.focused` state and deliver the layer focus/blur callbacks.
`Window.primaryLayer` returns the native `Layer` object registered as that window's primary layer and reports an error when the window has no primary layer.
`Window.getWindowRect()`, `getClientRect()`, and `getNormalRect()` return dictionaries with `x`, `y`, `w`, and `h`. `Window.drawDevice` retains the script-facing object value; headless sessions default it to `null`. The `drawdeviceD3D` plugin classes are available on request as CPU-backed image/layer composition (see below), but linking the plugin does not replace the window's draw device or enable KAG's Direct3D mode.

## Timer and event natives

[`timer_native.go`](../internal/runtime/timer_native.go) wraps runtime timers with `ActionOwner`/optional `ActionName`, fixed-point millisecond intervals, enabled/capacity/mode properties, and deferred callback delivery. The bridge covers bounded `normal`, `exclusive`, and `idle` modes; other C++ action-dispatch extensions are not implemented.

[`rect_native.go`](../internal/runtime/rect_native.go) implements four-edge `Rect` operations/properties. `Rect.nativeArray` returns a fresh safe TJS array rather than a C++ raw native pointer. [`async_trigger_native.go`](../internal/runtime/async_trigger_native.go) uses the runtime event queue for cached/coalesced delivery and bounded event priorities.
An empty `ActionName` calls `ActionOwner` itself; a non-empty name calls that owner member. Both forms receive one event dictionary with `type` set to `"onFire"` and `target` set to the trigger.

## Built-in plugin links

`Plugins.link` records plugin paths using slash-normalized, case-insensitive keys; `.tpm` and `.dll` names share a key, and `KAGParserEx` resolves to the built-in `KAGParser` module. Linking either `menu.dll` or `windowEx.dll` installs the shared headless `MenuItem` surface; the latter also exposes the WindowEx bitmap constants without loading external libraries. `KAGParser` and WindowEx-compatible `Window` methods are already registered by the session, so their built-in plugin links preserve the compatibility surface. The portable Window surface includes Win32 notification name/number lookup, non-client hit-test constants, extended event/hook state, geometry, and a retained `exSystemMenu` description. `Window.bringToFront()` and `Pad.bringToFront()` are accepted as host-neutral no-ops; icon, overlay, `bringTo`/`sendToBack`, menu-focus, and non-client hit-test functionality are explicitly unsupported.


`extrans.dll` remains a link-only capability because its transition providers are outside the current runtime surface. `extNagano.dll` is also link-only at the plugin layer, while its `spin` provider is implemented by `Layer.beginTransition` with `time`, `type1`, `type2`, and `accel` options; `crossfade` and `universal` remain available as built-in providers.
`ScriptsEx.dll` is recognized as a built-in compatibility link and is recorded idempotently using the same normalized key. The session exposes the generic `Scripts` helpers (`getObjectKeys`, `getObjectCount`, `getMD5HashString`, `equalStruct`, `equalStructNumericLoose`, `foreach`, `clone`, `getObjectContext`, and `isNullContext`), the upstream property-flag constants, and the bounded property/storage surface: `propGet`, `propSet`, `safeEvalStorage`, and `rehash`. Accepting the link records compatibility; the methods are registered on every session because the runtime implements them in Go rather than loading the DLL.

Two further link-only names are accepted because the runtime already provides the capability the module supplies, and the reference modules register no TJS surface of their own:

- `krmovie.dll` backs the core `VideoOverlay` class in krkrz (`krkrz/movie/win32/krmovie.cpp` implements `GetVideoOverlayObject`), and the portable reference keeps that backend in the core (`cpp/core/movie/ffmpeg/krffmpeg.cpp`; `TJS_W("VideoOverlay")` is registered by `cpp/core/base/ScriptMgnIntf.cpp:496`). The Go runtime likewise owns `VideoOverlay` and decodes its MPEG, ASF/WMV, and AMV sources itself, so the link installs nothing and creates no compatibility class.
- `wuvorbis.dll` adds Ogg Vorbis decoding to the Windows core; here that decoding is already in the core sound path (`WaveSoundBuffer` through the FFmpeg sidecar, whose build enables `--enable-decoder=vorbis`).

Windows-only modules are deliberately not answered, because macOS/Linux cannot load the shipped DLLs and the runtime holds no cross-platform implementation of their behavior. Linking them reports the unavailable module instead of a false success, matching the reference plugin managers, which register nothing for an unknown module (`krkrz/base/win32/PluginImpl.cpp:442` throws; `cpp/core/plugin/ncbind.cpp:12` returns false):

- `win32ole.dll` (COM/OLE automation) and `wuopus.dll` (Opus decoding): neither reference nor the runtime provides the capability; the FFmpeg sidecar decodes no Opus.
- `krkrsteam.dll` and `steamdrawdevice.dll` (Steamworks integration and draw device): only compiled in the portable reference when the Steam SDK is enabled (`cpp/plugins/CMakeLists.txt:23`).
- `k2compat.dll` (KAG's krkrz-only window/console compatibility plugin) and `kagexopt.dll`: absent from both reference plugin inventories, and no runtime facility supplies their exports.


The small compatibility links `getabout.dll`, `win32dialog.dll`, and `fftgraph.dll` use the same case-insensitive `.dll`/`.tpm` path normalization:

`getabout.dll` exposes `System.getAboutString()` (`cpp/plugins/getabout.cpp:4-5`). This method is registered when each Session is initialized and is callable before or after the plugin link; linking records plugin compatibility rather than dynamically adding the method. It returns the existing Go version-information value because the runtime has no executable about-resource/important-log input; it does not synthesize resource text. The reference `TVPGetAboutString` formats version-resource content and appends important logs (`msg/MsgIntf.cpp:162-175`; resource reader `win32/MsgImpl.cpp:45+`).

`win32dialog.dll` evaluates a portable `WIN32Dialog` class. It supports dialog templates, common controls used by K2Compat, text editing, combo-box history notifications, and an Ebitengine overlay; the host IME is connected through Ebitengine's text-input Composer. `initCommonControlsEx` reports the portable controls as available. `messageBox(message, caption, type)` routes through the host dialog handler and returns true, matching `!System.inform(...)` when that void-returning call completes; absent a handler it returns `ErrDialogUnavailable`.

`fftgraph.dll` installs the global `drawFFTGraph()` (`cpp/plugins/fftgraph.cpp:5-7`). The C++ function is an empty no-op, but the Go runtime has no FFT renderer contract, so invoking it returns an explicit unsupported-device error rather than implying that a graph was drawn.

## Portable Pad compatibility

Each runtime session registers a host-neutral `Pad` native class. The compatibility surface retains text, title, style, visibility, and geometry properties per instance, and implements `clear`, `print`, `setPos`, `setSize`, `show`, `hide`, and `registerExEvent` for scripts such as `LogWindowPad` and `ShowDebugHelp`. It does not create an operating-system text editor or claim that content was painted; `print` is accepted as a rendering request while script-visible state remains available. This permits portable scripts to construct and manage log/help pads without relying on the Windows UI.

Reference comparison: krkr2's `cpp/core/utils/PadIntf.cpp` defines the baseline native class/property surface, with `cpp/core/impl/PadImpl.*` supplying its platform-specific implementation; the inspected krkrz tree exposes gamepad input rather than this script class, and krkrz_rs's Win32Dialog registry is separate. The game's `system/logwindow.tjs` subclasses `Pad` and relies on text, status, styling, geometry, clearing, and print/update operations; `sysscn/debugutil.tjs` also constructs `Pad` directly and sets visibility/text/geometry. `win32dialog.dll` is a separate optional `WIN32Dialog` plugin linked by `initialize.tjs`, not the implementation of Pad.

## Graphics and media plugin compatibility

The krkr2 C++ plugin sources expose substantially larger APIs than the Go host currently implements. The Go runtime has a bounded PSD parser, no GDI+/Anti-Grain `layerExDraw` renderer, and no native video presentation backend for the `layerExMovie` Layer extension. It does already provide general-purpose PNG/JPEG/BMP image loading/saving, Layer image operations, XP3 archive reading, a PSB object-tree parser, and a headless `VideoOverlay` path; these facilities are not aliases for the plugin-specific formats or presentation behavior.

- `drawdeviceD3D.dll` and `drawdeviceD3DZ.dll` register the Neko D3D surface: `D3DImage` (`load` from a Layer, Bitmap, or D3DImage, plus `width`/`height`), `D3DPicture` (constructor, `assignImageRange`, `clearImageRange`, `setCoord`, `draw`, `opacity`, `blendMode`), `D3DLayer` (constructor, `setMatrix`, `setClip`, `draw`, `update`, `drawPlane`, `visible`, `frontIndex`, `backIndex`, `opacity`, and the `DrawPlaneFront`/`DrawPlaneBack`/`DrawPlaneBoth` constants), `D3D`, and `DrawDeviceD3D` (dimensions, clear color, screen/primary rectangles, offset, layer list, `update`, `capture` into a Layer, transitions, and stretch parameters). Images and layers are backed by CPU RGBA buffers and the runtime's existing integer blender (`drawdevice_d3d_native.go`), so `system/d3d.tjs` can derive `D3DRefImage` and `D3DAffineLayer` even when the software draw device is active. `checkEnable` truthfully reports that no e-mote or motion D3D modules are available and `getModule` returns `void`; `getPrimaryLayerBitmap` is not exposed. KAG's Direct3D mode still requires the regular `Layer` class to supply the reference `drawPlane`/`frontIndex`/`backIndex` properties, so the runtime leaves that mode opt-in rather than fabricating a window-integrated Direct3D device.
- `psbfile.dll` registers `PSBFile` with `load` and `root` (`cpp/plugins/psbfile/main.cpp`) and is served by the runtime's own PSB parser (`internal/assets/psb.go`).

This is runtime-local registration, not host OS font installation; the optional `private` argument does not change that scope.
- `fstat.dll` adds `Storages` file/directory metadata and mutation helpers (`cpp/plugins/fstat/main.cpp`). Go implements `fstat`, `getTime`/`setTime`, last-modified timestamps, `exportFile`, `deleteFile`, `truncateFile`, `moveFile`, `dirtree`, directory creation/removal, attribute get/set/reset, `isExistentDirectory`, `copyFile`/`copyFileNoNormalize`, `isExistentStorageNoSearchNoNormalize`, `getDisplayName`, `searchPath`, and `clearStorageCaches`. Mutations use the save overlay; packaged files and archive members are read-only. `changeDirectory` and `selectDirectory` report `ErrUnsupportedDevice`; hidden/system/temporary attributes are unsupported; read-only is the portable persisted bit. `getMD5HashString` and the `currentPath` property remain unavailable. `xp3filter.dll` is an archive-filter plugin (`cpp/plugins/xp3filter.cpp`) with repacking/filter-script behavior and is not installed by linking the name. The Go XP3 archive reader remains available through normal storage access.
- `wutcwf.dll` decodes TCWF0 ADPCM sources (`cpp/plugins/wutcwf.cpp`). `WaveSoundBuffer.OpenBytes` detects the `TCWF0\x1a` signature and decodes in-process before the FFmpeg path; mono/stereo, block peak correction, and source-rate transport are covered. Channels above two, rates above 768000, and a missing declared block are explicit errors; TCWF carries no loop metadata.

Unimplemented plugin calls continue through the normal unsupported-native path unless a method is explicitly routed to a device limitation, as with the `layerExMovie` methods. Plugin-name tracking is not a promise that those plugin APIs are available.

## Script and data plugin compatibility

The built-in `Scripts` class includes the pure-Go `ScriptsEx` helpers `getObjectKeys`, `getObjectCount`, `getMD5HashString`, `equalStruct`, and `equalStructNumericLoose`. Object keys are returned in deterministic UTF-16 order; structural equality recursively compares arrays and dictionaries, and the numeric-loose variant also equates integer and real numeric values. `getMD5HashString` accepts an Octet and returns lowercase hexadecimal MD5. The core VM serialization registration provides `saveStruct`/`saveStruct2` and `toStructString` for arrays and dictionaries, with the existing `Array.save`/`load` binary serialization surface kept separate. `TextRenderBase` is a built-in TJS native backed by Go text-render state, not an external DLL.
`Scripts.foreach(object, callback, extra...)` invokes callbacks with each key and value, followed by the explicitly supplied `extra` arguments. It does not implicitly pass the traversed object to the callback.

`Scripts.propGet(object, name, flags?)` and `Scripts.propSet(object, name, value, flags?)` dispatch through the VM's own member resolver with the C++ defaults: `propGet` defaults to `pfMemberMustExist`, `propSet` to `pfMemberEnsure`. `pfMemberEnsure` reads create a `void` member when one is missing; `pfIgnoreProp` reads return the raw property descriptor and writes replace it; `pfHiddenMember` and `pfStaticMember` record the corresponding member flags, so hidden members are omitted from `getObjectKeys` and from a `foreach` callback whose flag word is exactly `pfHiddenMember` (the reference callback tests equality rather than the bit), while they still count in `getObjectCount`; static class members are not inherited by instances. Missing members follow the reference split: custom objects and classes report `TJS member not found`, while a dictionary read without `pfMemberMustExist` and an out-of-range or negative-out-of-range array read yield `void`. Array keys use the reference array rule (integer and numeric-string keys, negative indexes counted from the end, `PropSetByNum` growth). A property without the required getter or setter reports `TJS access denied`. As in the C++ callback, `propGet` rejects a discarded result for plain data members but permits it after running a getter; dictionaries' optional missing read may also be discarded.

Two member-model differences remain. C++ copies non-static class members into each instance at construction, while Go resolves class members dynamically, so an instance created before a member is marked `pfStaticMember` also stops seeing that member. For `propSet` with `pfMemberEnsure`, C++ writes an existing superclass member first and creates a local member only when no inherited member exists; Go materializes or writes on the receiver class. A null receiver closure reports `expected object closure`; the C++ path dereferences it as undefined behavior.

`Scripts.safeEvalStorage(storage, mode?, context?)` reads the text storage (honoring an `oN` offset in `mode`), wraps the contents as `(const)[contents]`, evaluates it as an expression in `context` (or the global context), and returns element `0` with property dispatch ignored, matching `scriptsEx.cpp`. Empty storages therefore yield `void`. It reports storage, decode, and evaluation errors explicitly and never treats the input as compiled TJS2 bytecode. Only the `oN` offset mode is modeled; binary and encoding stream modes are not. `Scripts.rehash()` exists for source compatibility: C++ increments the global hash magic so custom objects rebuild hash chains, whereas Go members are map entries keyed by UTF-16 units, so there is no stale hash index to rebuild and the function returns `void`.

Linking `csvParser.dll` activates `CSVParser` (`cpp/plugins/csvParser.cpp`) with `init`, `initStorage`, `getNextLine`, `parse`, `parseStorage`, and read-only `currentLineNumber`. It returns TJS arrays, combines quoted physical lines using the configured newline string, supports doubled quotes and custom single-rune separators, and invokes `doLine(fields, recordNumber)` for parse calls. Storage input follows the runtime text decoder unless the UTF-8 flag is set, in which case bytes are interpreted as UTF-8. The Go CSV reader accepts malformed quote syntax with `LazyQuotes`; the C++ parser has its own permissive recovery rules, so malformed-input edge cases are not promised byte-for-byte identical.

Linking `varfile.dll` activates the `var://./...` storage subset (`cpp/plugins/varfile.cpp`). Paths traverse global TJS objects/dictionaries (including arrays by numeric member), leaf files must be Octet values, writes replace the leaf with an Octet, `Storages.isExistentStorage` checks Octet leaves, and `Storages.getListAt` returns Octet member names sorted deterministically. This maps the C++ in-memory stream's read/write and file-list behavior without host filesystem access. Domain names other than `.` are rejected; TJS object properties are the only directory representation, and `varfile` append/update seek modes, local OS paths, and non-Octet stream values are not exposed by this text/storage API. Linking either name does not load an external DLL.
## C++ comparison and semantic limits

- Unsupported native/device calls return errors rather than silently succeeding. Dialogs, file dialogs, and shell execution require handlers supplied by a host; absent handlers report unavailable errors.
- `System.versionString`/`versionInformation` are stable `krkrgo` project values. `platformName` is the deterministic `GOOS/GOARCH` value.
- Without a platform system-color table, `System.toActualColor` preserves the low 24-bit RGB payload instead of applying a C++ system-color mapping.
- `System.exit` records the requested code and returns `ErrSystemExit`; a Go library does not terminate its embedding process.

Graphics natives are detailed in [Graphics, layers, and text](graphics-layer-text.md); sound/video natives are in [Audio and video](audio-video.md).

**C++ reference:** [Kirikiri Z source](https://github.com/krkrz/krkrz). The runtime APIs here model a bounded Go subset and do not imply full native API parity.
